# Stratum 设计文档

> 面向 RAG 场景的分布式知识库存储系统
> 本文档记录系统的设计方向、数据模型、模块职责和关键流程，不包含代码层面的实现细节。

---

## 系统定位

Stratum 是一个面向 RAG 场景的分布式知识库存储系统，解决知识库的版本管理问题。

**用户是知识库的管理者**，不是最终的对话用户。系统解决的核心问题是：

- 知识库更新出错时能快速回滚
- 多版本并存时支持 A/B 测试
- 审计：某次召回结果是基于哪个版本的知识库产生的

对话历史、用户会话管理属于上层应用的职责，不归 Stratum 管。

---

## 核心概念

### 知识库

知识库是 Stratum 管理的基本单位。一个系统里可以有多个知识库，每个知识库有独立的版本历史。

### 版本

每次对知识库的变更产生一个新版本。版本之间有父子关系，形成一条版本链，允许分叉（同一父版本可以有多个子版本，支持 A/B 测试场景）。每个知识库同一时刻只有一个活跃版本，查询默认打到活跃版本。

### 文档

调用方操作的基本单位。文档有唯一的文档 ID，内容是原始文本。Stratum 对外暴露的操作粒度是文档。

### Chunk

Stratum 内部的存储和向量搜索单位，对调用方不可见。文档在写入时被切成若干 chunk，Stratum 内部调用 embed 服务生成每个 chunk 的向量。chunk 是内容寻址的，通过哈希唯一标识，同一知识库内相同文本 + 相同 embed 配置的 chunk 只存一份。

## 对外接口

### 知识库管理

| 操作 | 入参 | 返回 |
|---|---|---|
| 创建知识库 | 知识库名称、切割窗口大小、重叠大小、embed 服务配置 | 知识库 ID、初始版本 ID |
| 删除知识库 | 知识库 ID | 成功 / 失败 |

### 版本管理

| 操作 | 入参 | 返回 |
|---|---|---|
| 创建新版本 | 父版本 ID、文档变更列表 | 新版本 ID |
| 查询版本列表 | 知识库 ID | 版本列表（版本 ID、创建时间、父版本 ID） |
| 回滚到某个版本 | 目标版本 ID | 成功 / 失败 |

文档变更列表中每条记录包含：
- 操作类型：ADD / DELETE / UPDATE
- 文档 ID
- 文本内容（DELETE 时不需要）

调用方应将一次业务更新的所有文档变更打包成一个变更列表传入，一次 `CreateVersion` = 一个版本 = 一次索引构建。向量由 Stratum 内部调用 embed 服务生成，调用方不感知 chunk 边界。

### 查询

| 操作 | 入参 | 返回 |
|---|---|---|
| 向量查询 | 版本 ID、查询向量、top_k、相似度阈值（可选） | 文档列表（文档 ID、原始文本、相似度分数） |

查询向量由调用方使用 embed 模型生成后传入，Stratum 不感知向量的生成方式，只负责检索。

## 存储层设计

### 数据分层

```
┌─────────────────────────────────────────────────┐
│               版本元数据                          │  ← Raft 状态机，强一致
│   版本 ID / 父版本 / 索引构建状态 / 版本计数器    │
└─────────────────────────────────────────────────┘

┌──────────────────┐  ┌───────────────────┐  ┌─────────────────────┐
│    doc store     │  │  chunk-doc 映射   │  │   版本文档列表       │  ← PebbleDB（Go），磁盘持久化
│ 文档原始文本      │  │  chunk ↔ 文档 ID  │  │  版本 ID → 文档 ID  │
└──────────────────┘  └───────────────────┘  └─────────────────────┘

┌───────────────────┐  ┌─────────────────────────────────┐
│    chunk store    │  │         HNSW 索引               │  ← RocksDB / Faiss（C++ vecstore），
│   chunk 向量       │  │       向量近似搜索               │     磁盘持久化，Go 侧通过内部 gRPC 访问
└───────────────────┘  └─────────────────────────────────┘

┌──────────────────────────────┐  ┌─────────────────────────────────┐
│  chunk 存在性布隆过滤器       │  │   版本文档布隆过滤器              │  ← 内存，崩溃后重建
│  每个知识库一份               │  │   每个版本一份                   │
└──────────────────────────────┘  └─────────────────────────────────┘
```

### 版本元数据（Raft 状态机）

每个版本记录：
- 版本 ID
- 父版本 ID
- 创建时间（leader apply 时的本地时间戳，不要求跨节点严格单调）
- 索引构建状态（PENDING / READY / FAILED）

版本元数据体积小、一致性要求高，存在 Raft 状态机里，通过 Raft 日志复制保证多副本一致。版本计数器也维护在 Raft 状态机中，保证版本 ID 单调递增。

**索引状态说明**：

| 状态 | 含义 |
|---|---|
| PENDING | 元数据已分配，存储层写入进行中，不可查询 |
| READY | 索引构建完成，可查询 |
| FAILED | 构建失败，可通过 RebuildIndex 重新触发 |

WAL 的 COMMIT 记录作为"存储层写入已完成"的唯一标志，崩溃恢复时凭此判断是否需要重放存储写入或直接触发索引构建。

### 版本文档列表（PebbleDB）

- key：`知识库 ID + 版本 ID + 文档 ID`
- value：空

记录每个版本包含的全量文档 ID。写入时从父版本 VersionDocList 前缀扫描拿到全量文档 ID，应用本次变更（ADD 追加、DELETE 移除、UPDATE 替换文档 ID 不变），将最终全量文档 ID 集合写入新版本。写入天然幂等。读取时按 `知识库 ID + 版本 ID` 前缀扫描，拿到该版本所有文档 ID。GC 时按版本 ID 前缀清理旧版本条目。

### 布隆过滤器

**版本文档布隆过滤器**：每个版本一份，内容为该版本全量文档 ID 集合。读路径用于快速过滤不属于目标版本的文档 ID，命中后再去版本文档列表确认（处理假阳性）。随版本创建时构建，持久化到磁盘，崩溃后从版本文档列表重建。

**chunk 存在性布隆过滤器**：每个知识库一份，内容为该知识库已存在的 chunk ID 集合。写路径用于判断 chunk 是否已存在，不在则直接写入，在则去 chunk store 确认（处理假阳性）。崩溃后从 chunk store 重建。

### doc store（PebbleDB）

- key：`知识库 ID + 文档 ID + 版本 ID`
- value：完整文档原始文本；DELETE 操作写入墓碑标记（空 value）

**版本 ID** 是每个知识库独立维护的单调递增整数，通过 Raft 状态机中的版本计数器分配，保证全序。

**写入语义**：只有发生变更（ADD / UPDATE / DELETE）的文档才写入新记录，未变更的文档不产生新条目。

**读取语义**：查询某版本的某篇文档时，按 `知识库 ID + 文档 ID` 前缀扫描，取版本 ID ≤ 目标版本 ID 中最大的一条。若该条为墓碑标记，则认为文档在此版本已删除，不返回内容。

**存储放大**：每次变更只写一条记录，未变更文档零开销。

**GC**：清理版本 ID ≤ 保留下限的条目时，需先为每篇文档在保留下限处写入一条最新快照，再删除更早的条目，防止读穿。删除知识库时按 `知识库 ID` 前缀扫描清理。

### chunk store（RocksDB，C++ vecstore）

- key：`知识库 ID + chunk ID`，chunk ID 即 `SHA-256(chunk 文本 + embed 配置 ID)`
- value：chunk 对应的向量

chunk 是内容寻址的，相同文本、相同 embed 配置切出来的 chunk 在同一知识库内只存一份。哈希冲突概率极低（SHA-256），忽略不处理。

chunk 向量的权威存储在 C++ vecstore 的 RocksDB 中，Go 侧通过内部 gRPC 访问，不在 PebbleDB 中存储向量数据，无数据冗余。

### chunk-doc 映射（PebbleDB）

维护两个方向的 key，在同一次写入中一起更新：

- 正向：`知识库 ID + chunk ID + 文档 ID`，value 空。读取时按 `知识库 ID + chunk ID` 前缀扫描，拿到该 chunk 关联的所有文档 ID（供 Query 读路径使用）
- 反向：`知识库 ID + 文档 ID + chunk ID`，value 空。读取时按 `知识库 ID + 文档 ID` 前缀扫描，拿到该文档关联的所有 chunk ID（供 IndexManager 异步构建批量反查使用）

写入天然幂等，并发写入不同文档的映射关系不会冲突。删除知识库时按 `知识库 ID` 前缀扫描清理两个方向的条目。

**异步 GC**：文档 DELETE 后，doc store 写入墓碑，但 chunk-doc 映射中该文档的正向和反向条目不立即清理。后台异步 GC 定期扫描：
1. 扫描正向索引，对每个 `知识库ID + chunkID`，检查对应文档在当前最老保留版本中是否已全部被删除
2. 若是孤儿 chunk（无任何存活文档引用）：先删 ChunkDocMapper 正向+反向条目，再通过内部 gRPC 调用 `ChunkStore.Delete(kbID, chunkID)` 删除 vecstore 中的向量；先删映射、后删向量，确保崩溃后重试幂等
3. 若仍有存活文档引用：只清理已删除文档的映射条目，保留 chunk 向量

GC 间隔可配置，对主路径无影响。

### 向量索引

每个版本维护一份完整的向量索引。索引类型和相似度计算方式是**知识库级别的固定属性**，创建知识库时指定，创建后不可变；所有版本继承知识库的索引类型和相似度方式，不支持版本级覆盖。变更索引类型等价于换 embed 配置，需要创建新知识库并由调用方迁移数据。

**当前实现**：仅 HNSW，相似度默认余弦相似度。IVF / FLAT 作为接口预留，暂不实现。

HNSW 图结构是全局的，节点之间的连接在整个索引范围内建立，无法跨版本共享。每次 CreateVersion 触发一次全量 HNSW 重建。

**磁盘保留策略**：最近 N 个版本的索引持久化在磁盘，N 可配置。更老的版本索引删除，需要时重建。

**多副本构建**：每个副本独立异步构建自己的 HNSW 索引。HNSW 构建过程本身有随机性，不同副本的图结构可能不完全相同，但召回质量等价，无需同步。

**内存管理**：由索引管理器负责，详见下节。

## 索引管理器

索引管理器负责管理内存中的活跃 HNSW 索引，对查询层透明。

### 内存换入换出

- 采用 LRU 策略，最久未访问的版本索引优先换出
- 后台监控内存占用，超过阈值后设置标志位
- 每次新索引加载时检查标志位，若已超阈值则先换出再加载

### 换出前置条件

每个索引维护引用计数，记录当前有多少查询正在使用该索引。只有引用计数为 0 的索引才能换出。换出时按 LRU 顺序遍历，跳过引用计数不为 0 的候选，找到第一个可换出的执行换出。

### 并发加载

多个查询请求同时访问同一个冷版本索引时，只触发一次加载，其余请求等待共享结果。

若所有内存中的索引引用计数均不为 0，新加载请求等待，直到有索引引用计数归零可换出。等待超时后返回错误，由调用方决定重试策略。

### 索引异步构建

HNSW 索引构建不作为写事务的一部分，而是在 WAL COMMIT 后异步执行：

**构建数据来源**：
1. `VersionDocList.ListDocIDs(kbID, versionID)` 拿到该版本全量文档 ID
2. `ChunkDocMapper.ListChunkIDsByDocs(kbID, docIDs)` 批量反查全量 chunk ID，合并去重
3. 批量通过内部 gRPC 从 vecstore chunk store 读取向量
4. 喂给 HNSW 构建

**构建期间**：查询请求继续使用上一个已构建完成的版本索引提供服务，新索引在后台构建，不影响查询。

**构建完成**：原子切换到新索引，旧索引等引用计数归零后释放。索引状态通过 Raft propose 更新为 READY；若构建失败，状态更新为 FAILED，记录日志和指标，可通过 `RebuildIndex` 手动触发重建。

**崩溃恢复**：重启后发现 WAL 有 COMMIT 记录但版本状态仍为 PENDING：
- 若索引文件已存在：直接 propose 状态更新为 READY，跳过重建
- 若索引文件不存在：重新触发异步构建

## 写路径

### 文档切割与向量生成

文档写入时，Stratum 内部按滑动窗口策略切割成 chunk：

- 窗口大小和重叠大小在创建知识库时由调用方配置
- 对每个 chunk 计算 `SHA-256(chunk 文本 + embed 配置 ID)` 作为 chunk ID
- 切割完成后 Stratum 内部调用知识库绑定的 embed 服务生成每个 chunk 的向量
- 文档长度小于窗口大小时，整篇文档作为一个 chunk

### 事务保证（WAL）

写路径使用 WAL 保证崩溃一致性，事务边界如下：

**关键时序约束**：Raft 状态机 apply `ProposeCreateVersion` 时，必须先同步写入 `WAL.WriteVersionID(versionID)`，写入成功后才更新状态机内存状态。`WriteVersionID` 对同一 versionID 重复写入幂等（直接返回成功）。此约束保证：WAL 有 VERSION_ID 记录时状态机里一定有对应版本，不会产生孤儿版本。

**事务内（同步完成，调用方阻塞到第 7 步完成后返回）**：
1. WAL 写入 BEGIN 记录
2. 版本元数据提交 Raft（`ProposeCreateVersion`）；Raft 状态机 apply 阶段先写 WAL VERSION_ID 记录，再分配新版本 ID 并写入状态机，阻塞到多数派确认并 apply 完成后返回 versionID
3. 对每个变更文档切割 chunk，调用 embed 服务生成向量；对每个 chunk，查 chunk 存在性布隆过滤器：不存在则通过内部 gRPC 写入 vecstore chunk store 并更新布隆过滤器；存在则通过内部 gRPC 去 chunk store 确认，确认不存在才写入。chunk-doc 映射写入 PebbleDB（正向+反向，幂等）
4. 文档原始文本写入 doc store（key 含第 2 步分配的版本 ID）
5. 版本文档列表写入 PebbleDB：从父版本 VersionDocList 前缀扫描拿到全量文档 ID，应用本次变更，将最终全量文档 ID 集合写入新版本（key 含新分配的版本 ID）；构建版本文档布隆过滤器并持久化
6. WAL 写入 COMMIT 记录（含版本 ID）

**事务外（异步）**：
7. HNSW 索引异步构建（VersionDocList → ChunkDocMapper 批量反查 → 批量读向量 → 构建）
8. 构建完成后版本状态 propose 更新为 READY；构建失败则更新为 FAILED，记录日志和指标

### 幂等性

- chunk store 写入：内容寻址，重复写入同一 key-value 结果不变，天然幂等
- chunk-doc 映射写入：key 包含文档 ID（正向）/ chunk ID（反向），重复写入幂等
- doc store 写入：key 包含版本 ID，重复写入幂等
- 版本文档列表写入：key 包含文档 ID，重复写入幂等
- WAL.WriteVersionID：同一 versionID 重复写入幂等
- Raft 提交：由 Raft 本身保证幂等

崩溃恢复时，WAL 重放逻辑：
- 有 BEGIN 但无 VERSION_ID：Raft propose 未完成（apply 前崩溃），重新 propose；状态机里没有对应版本，无需清理
- 有 VERSION_ID 但无 COMMIT：跳过 Raft propose，使用 WAL 记录的版本 ID 从头重放所有存储写入（步骤 3-6），每一步均可安全重放
- 有 COMMIT 但版本仍为 PENDING：检查索引文件是否存在，存在则 propose READY，不存在则触发异步构建

## 读路径

### 完整流程

1. 收到版本 ID + 查询向量 + top_k + 相似度阈值 + chunk 聚合方式（可选，默认中位数）
2. 索引管理器加载目标版本 HNSW 索引（LRU 换入），引用计数加 1
3. HNSW 搜索返回 top_k × N 个 chunk ID 和相似度分数
4. 过滤低于相似度阈值的结果
5. 对每个 chunk ID 前缀扫描 chunk-doc 映射，拿到所有关联文档 ID
6. 按文档 ID 分组，同一篇文档命中多个 chunk 时按指定聚合方式（最高分 / 中位数 / 平均分）计算分数，去重
7. 查版本文档布隆过滤器，过滤不属于目标版本的文档 ID；布隆过滤器命中的去版本文档列表确认
8. 按分数排序，取前 top_k 篇文档
9. 对每个文档 ID 扫描 doc store，取版本 ID ≤ 目标版本 ID 的最大条目，拿到完整文档文本
10. 引用计数减 1，返回文档 ID、原始文本、相似度分数

### 结果数量

若去重后文档数量不足 top_k，直接返回现有结果，不强求数量。相似度低于阈值的结果不返回。

## 版本回滚

### 流程

1. 调用方发起回滚请求，指定目标版本 ID
2. 校验目标版本属于同一知识库且索引状态为 READY
3. Stratum 通过 Raft 提交活跃版本切换，更新知识库元数据中的活跃版本 ID
4. apply 完成后活跃版本切换生效
5. 上层应用服务器通过轮询感知活跃版本变化，后续请求切换到新版本
6. 旧版本索引引用计数归零后，由 LRU 自然换出

### 不停服

回滚期间正在进行的查询通过引用计数保护，继续使用旧版本索引直到完成。新请求在活跃版本切换后打到目标版本索引。两个版本索引短暂共存，无需停服。

版本切换通知采用轮询而非回调，避免网络异常或重启导致信号丢失。

### 版本链约束

- 父版本必须属于同一知识库
- 父版本不能是 PENDING 状态
- 允许分叉（同一父版本可以有多个子版本），支持 A/B 测试场景

## 删除知识库

删除操作需要清理四类数据，采用 WAL 标记保证崩溃后可继续清理：

1. WAL 写入删除记录，持久化
2. Raft 提交知识库状态标记为删除中，拒绝新的查询和写入
3. 清理内存中的 HNSW 索引及布隆过滤器
4. 清理磁盘上的 HNSW 索引文件及版本文档布隆过滤器（文件不存在时忽略，幂等）
5. 清理 doc store 中该知识库所有版本的文档数据
6. 清理 chunk store 和 chunk-doc 映射中该知识库所有 chunk（含孤儿 chunk 向量）
7. 清理版本文档列表中该知识库所有条目
8. 清理 Raft 状态机中的版本元数据（`ProposeRemoveKBMeta`；若元数据已不存在则视为成功，幂等）
9. WAL 写入删除完成记录

崩溃恢复时，发现 WAL 有删除记录但没有完成记录，从第 3 步继续执行。第 4 步文件删除忽略 `ErrNotExist`，第 8 步 `ProposeRemoveKBMeta` 忽略 `ErrKnowledgeBaseNotFound`，保证每一步均可安全重复执行。

**永久性错误处理**：每一步失败后指数退避重试，重试次数耗尽后将知识库状态标记为 `DeleteFailed`，暴露给 `GetSystemStatus`，由运维人工介入。WAL 记录保留，方便后续离线工具重新执行清理。

## 未来分片架构（预留）

当前设计是单 Raft 集群，所有知识库的版本元数据由同一个 Raft group 管理。这在中型企业、知识库数量在几十到上百量级时不构成瓶颈。

如果未来需要分片（多个 Raft group，每组管理一部分知识库），架构上预留以下设计点：

- **分片映射结构**：知识库 ID → Raft group ID 的映射关系。由于所有存储层 key 都以知识库 ID 为前缀，数据本身天然按知识库隔离，分片时不需要重新设计 key 结构，只需按知识库 ID 划分到不同 Raft group。

- **RaftNode 接口不变**：当前 `RaftNode` 接口封装单个 Raft 集群的操作。分片后，Service 层从持有单个 `RaftNode` 实例变为持有"`RaftNode` 实例集合 + 路由表"，`RaftNode` 接口本身保持不变，分片对接口零侵入。

## 待细化的问题

- HNSW 索引构建触发后的默认超时时间
- 相似度阈值的默认值设定
- IVF / FLAT 索引的真实实现：Faiss IVF 需要训练阶段（k-means 聚类中心），FLAT 无索引结构、查询为暴力计算，二者的构建流程和内存管理策略与 HNSW 差异较大，需要单独设计
- 审计日志模块：`AuditLogger` 接口、存储 key 设计、`GetAuditLog` 读取实现。当前 `Query` 链路中的"异步写入审计日志"为占位步骤，不影响主链路，可后续增量添加。**已知限制**：审计日志异步写入失败仅记 ERROR 日志，存在丢失风险，不适用于强合规审计场景
- HybridQuery / Bleve 混合查询：Bleve 关键词索引的构建时机、是否按版本隔离、与现有 IndexManager 的索引生命周期管理是否统一
